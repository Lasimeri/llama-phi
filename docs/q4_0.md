# Q4_0 on the card, and the split layout

Measured 2026-11-09 on the hardware of [results.md](results.md) with an
RTX 3090 Ti beside the card. The model is a 27 B parameter Q4_0 GGUF
(15.7 GB) of the Qwen3.8 family; any Q4_0 model of that shape behaves
the same.

## What was missing

The card's matrix service took eight weight types: F32, F16, BF16,
Q4_K, Q5_K, Q6_K, Q8_0 and IQ4_XS. Q4_0 was not among them, so a Q4_0
model's matrices stayed with the host whatever the card's budget was.
Counted from the GGUF header (`tools/ggufcensus.c`):

| Tensors a matrix multiply reads | Count | Bytes |
|---|---|---|
| Q4_0 | 496 | 13,697,187,840 |
| Q6_K | 1 | 1,042,944,000 |
| F32 | 48 | 7,864,320 |
| total | | 14,747,996,160 |

The backend offered the card 1.0 GB (the one Q6_K matrix) and the card
kept half of it, 0.52 GB: 3.5 % of the matrix bytes. The host then has
to keep 14.2 GB of weights resident beside a 128K context; on 32 GB of
RAM it cannot, and every token re-reads part of the file from disk.

## The kernels

`patches/intel-phi-avx-512-c.patch` adds the type (`VPU_MM_Q4_0`, 8) and
six kernels, `phi_q4_0_{1,4,8}` and their float16-activation twins, to
the card worker; the type map, the row size and the name to the ggml
backend; and the type to the check tool. A Q4_0 block is 18 bytes: a
float16 scale `d`, then sixteen bytes whose low nibbles are weights
0..15 and whose high nibbles are weights 16..31, each `(q - 8) * d`.
A kernel call takes eight blocks (144 bytes, 256 weights) against 1, 4
or 8 activation rows:

| Step | On the vector unit |
|---|---|
| the eight scales | a masked expand-load with float16 up-conversion per block |
| the bytes | an unpack pair with uint8 up-conversion: sixteen floats, 0..255 |
| the high nibble | multiply by 2^-4, round down |
| the low nibble | fused negative multiply-add: `b - 16 hi` |
| `q - 8`, then `* d` | one subtract, one multiply by the block's scale |
| the products | one fused multiply-add per activation row |

Every value before the scale multiply is an exact small integer, and the
subtraction comes before the multiply, so a weight is rounded once, where
ggml's `dequantize_row_q4_0` rounds it: the card's weights equal the
reference's bit for bit. The six kernels are generated
(`tools/q4_0-kernels.c` in the patched repository, with its own
document). Rows whose length is not a multiple of 256 stay with the host.

Checks, all on the card:

- The worker's instruction audit: 0 illegal, 0 suspect of 20,139.
- `phi-vpu matmul-check -c 0 --only q4_0 --threads 114 --repeat 3`, with
  float32 and with float16 activations (`--act 1`): every case agrees
  with the host reference (plain multiplies at 1, 4, 8 and 13 activation
  rows, mixtures of experts, up to four matrices in one request, the
  fused feed-forward).
- The same check for Q8_0 afterwards: unchanged.

The card's compute time alone, 4096 x 5120, 114 threads, best of 3:

| Activation rows | float32 activations | float16 activations |
|---|---|---|
| 1 | 139.3 GFLOP/s (39.2 GB/s of weights) | 126.4 GFLOP/s (35.5 GB/s) |
| 8 | 246.4 GFLOP/s | 452.9 GFLOP/s |
| 64 | 251.3 GFLOP/s | 490.3 GFLOP/s |

## The split layout

Two unmodified llama-server processes on one model file, a slot file
between them (`scripts/split.sh`, `scripts/handoff.sh`):

```
╔═══════════════════════════════ desktop: Ryzen 7 5800X, 32 GB ════════════════════════════════╗
║  one chat request   ──▶ ┌─────────────────────────────┐                                      ║
║                         │ scripts/handoff.sh          │                                      ║
║                         └───────┬─────────────┬───────┘                                      ║
║          prompt, n-1 tokens     │             │   chat + cache_prompt                        ║
║                                 ▼             ▼                                              ║
║  ┌──────────────────────────────────┐   ┌──────────────────────────────────────────────┐     ║
║  │ llama-server :8091  (CUDA)       │   │ llama-server :8092  CUDA hidden, -t 8        │     ║
║  │ 27B Q4_0, 128K q8_0 context      │──▶│ every other op + 11.5 % of matrix rows       │     ║
║  │ prefill 364.65 tok/s             │   │ libggml_phi.so: MUL_MAT ─▶ K_MATMUL (kind 4) │     ║
║  └────────────────┬─────────────────┘   └──────────────────────┬───────────────────────┘     ║
║                   │ ──▶ = slot file, 519,778,808 B             │ /dev/shm/phi-hostmem        ║
║                   ▼                                            ▼                             ║
║  ╔══════════════════════════════════╗   ╔══════════════════════════════════════════════╗     ║
║  ║ RTX 3090 Ti   21,839 MiB in use  ║   ║ Xeon Phi 7120A  worker 28a264ae, 120 threads ║     ║
║  ║ weights + 128K context in VRAM   ║   ║ 13.09 GB of Q4_0 rows (88.5 %), pool 6437    ║     ║
║  ╚══════════════════════════════════╝   ║ phi_q4_0_{1,4,8}{,h}: 126-139 GFLOP/s at n 1 ║     ║
║                                         ║ generation 2.605 tok/s (was 0.2076)          ║     ║
║                                         ╚══════════════════════════════════════════════╝     ║
╚══════════════════════════════════════════════════════════════════════════════════════════════╝
```

The GPU server holds the model and the context in VRAM and processes
prompts. The decode server maps the same file with the GPU hidden; the
backend uploads to the card every row its budget holds and drops those
pages from the host (`PHI_GGML_OFFLOAD=1 PHI_GGML_ALL_ROWS=1`), so the
host keeps only what the card has no room for. Its line at load:

```
ggml-phi: 14.7 GB of dense weights and 0.0 GB of experts offered to the cards: each keeps 88.5% of every dense matrix's rows and 0.0% of the experts' (0 expert tensors a step more), 13.09 GB
```

```
PHI_VPU_HUGEPAGES=6437 scripts/worker.sh work
scripts/split.sh work MODEL.gguf prefill      # one terminal
scripts/split.sh work MODEL.gguf decode       # another
scripts/handoff.sh out docs/design.md 64 test.bin
```

`SPLIT_DRY=1` prints a server's command and environment without starting
it. The shim `work/runs/serve/libnopopulate.so` is used when it exists
(`gcc -O2 -shared -fPIC -o libnopopulate.so tools/nopopulate.c -ldl`,
[tools/nopopulate.md](../tools/nopopulate.md)).

## Measured

One request each, the same prompt (this repository's `docs/design.md`,
1,410 tokens with the chat template), the same servers, before and
after the kernels:

| | Card takes Q6_K only | Card takes Q4_0 |
|---|---|---|
| Rows on the card | 0.52 GB | 13.09 GB |
| Prefill on the GPU | 1,409 tokens, 348.61 tok/s | 1,409 tokens, 364.65 tok/s |
| Slot save, restore | 0.156 s, 0.119 s | 0.234 s, 0.170 s |
| First token on the decode server | 143.67 s | 34.24 s |
| Generation | 32 tokens, 0.2076 tok/s | 64 tokens in 24.183 s, 2.605 tok/s |

The slot file is 519,778,808 bytes and both servers report the same
1,409 tokens saved and restored. One run per configuration: there is no
spread to report, and the first-token times depend on how much of the
file the page cache held.

What worked when, sampled from the host every 500 us over the second
request (`tools/overlap.c`: the window's request and reply sequence
numbers, the request kind, the decode process's thread states; 100,608
samples, 62.9 s including the first token):

- 23,616 card requests, 0 errors. Each of the 22,439 the sampler caught
  was kind 4, a plain matrix multiply; none was a translated-code
  request (kinds 2 and 13).
- The card was busy 21.69 s: 20.27 s computing, 0.33 s pulling
  activations, 0.91 s pushing results.
- In 98.9 % of the samples with a multiply outstanding, all eight host
  threads were runnable. A thread that spins on the card's reply counts
  as runnable, so this shows the host active beside the card, not how
  much of that is row work.

## Limits

- 11.5 % of every matrix's rows stay on the host: the matrices are
  14.75 GB and the budget used here is 13.1 GB of a 16 GB card.
- Generation is bound by the card's compute: about 334 of the 384 ms a
  token, by the counters above.
- The fused feed-forward's gate on the host still names Q4_K to IQ4_XS,
  and the fused path is off under the offload in any case; the card side
  passes its check with Q4_0 in all three places.
- No Q4_0 tail routine: a row length must be a multiple of 256.
